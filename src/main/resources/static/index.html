How it works

OEE, the way the plant measures it

OEE = Availability × Performance × Quality
Availability
run time ÷ planned time (run time = planned − downtime)
Performance
ideal time for the units made ÷ run time (ideal time uses the line's rated units/hour)
Quality
good units ÷ total units produced

When a job order is closed with its run results, the API totals the logged downtime, computes all three factors, and stores the OEE — the same calculation a real line uses.

The domain

What the API covers

⚙️ Job orders & OEE

Plan, start, and close production runs. Closing computes Availability × Performance × Quality and stores it per order and per line.

⛔ Downtime & root cause

Log stoppages with minutes, reason, and root cause against a running job — they feed directly into the Availability factor.

🔬 QC holds

Raise and release quality holds with severity, tracked by who raised them and when — the quality team's workflow.

📦 FIFO inventory

Receive stock into lots and issue it oldest-lot-first (true FIFO), with an immutable movement ledger and on-hand balances.

Security

Role-based access (JWT)

MANAGER
Everything — create lines & job orders, plus all operator and QC actions.
OPERATOR
Start/close job orders, log downtime, receive and issue inventory.
QC
Raise and release QC holds.

Stateless HS256 JWTs carry the role as a claim; endpoints enforce it with Spring Security method security (@PreAuthorize).

Engineering

Built & tested like production

Layered service architecture, a Flyway-managed PostgreSQL schema that Hibernate validates against the entities, a self-contained H2 demo profile, and a real test suite — unit tests for the OEE math, MockMvc end-to-end flows, and a Testcontainers PostgreSQL integration test, all run by GitHub Actions on every push.
